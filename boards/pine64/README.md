# Jupiter on the original PINE A64+ 2 GB

This board port runs the complete Jupiter menu as an AArch32 EL1 bare-metal
payload behind the already validated `U-Boot 2025.10-jupiter-sd2` + TF-A handoff.
It carries the **46-entry menu** from `claude/sdk-review-cleanup-ok3job` at
`4fb5904e0563771a8225d554e8506d1df9b3f4f6`, including Jupiter Modes Tour,
DE2 capability probe and Mercury GPU Bring-Up. The earlier main-based package
has been superseded by this branch reconciliation.

## Use the delivered build

Write the delivered `jupiter-pine64-current.img` as a whole SD-card image,
then connect HDMI before power-on. Writing the image replaces that card's
contents, so copy any existing asset files first. The image already contains
the validated SD2 bootloader, TF-A, PINE64+ device tree and current menu.

For an existing working SD2 card, the optional `boot-update/` files replace
only `jupiter.uImage` and `boot.scr` on the first FAT partition. Keep its SD2
device tree and raw bootloader. The payload requires that explicit AArch32
EL1 handoff. The full image is 264 MiB: 8 MiB before partitions plus two
128 MiB FAT16 partitions. Most of that space is available filesystem capacity.

Connect HDMI before power-on. The menu uses a 480×272 logical canvas through
the inherited HDMI mode. A standard USB boot keyboard can use either socket;
serial UART0 at 115200 8N1 also controls the menu. Jupiter Modes Tour is first;
select Mercury GPU Bring-Up for the Pico/SpotPear test.

| Action | Keyboard/serial key |
|---|---|
| Menu up/down | Arrow keys or W/S |
| Open selection / A | Enter, Space or Z |
| B | X or Backspace |
| X / Y logical buttons | C / V |
| L / R | Q / E |
| Select / Start | 1 / 2 |
| N64 C directions | I / J / K / L |
| Reset to menu from a demo | Escape; USB/ANSI F12 also supported |

Mercury supports Enter/Z pause, C pattern/cube switch, V to read optional
bridge status, and X to return to the menu. On a local SPI-controller error,
Enter/Z retries. A missing Pico cannot be detected through this transmit-only
protocol; check its TV for the commanded colour and scene changes.
Most inherited animation demos run indefinitely; Escape/F12 uses a clean
firmware reset to reenter the picker. Finite board diagnostics return normally.

## Optional assets and external devices

The Mercury test, graphics demonstrations and included music examples do not
require external ROM files. The following synthesizer demos load user-provided
matching ROM sets from the **second FAT partition** (the asset volume):

| Demo | Path on asset volume | Required size |
|---|---|---:|
| MT-32 | `ROMS/MT32/CONTROL.ROM` | Matching supported control ROM, 64–256 KiB |
| MT-32 | `ROMS/MT32/PCM.ROM` | Matching supported PCM ROM, 512 KiB–2 MiB |
| SC-55 | `ROMS/SC55/ROM1.BIN` | 32,768 bytes |
| SC-55 | `ROMS/SC55/ROM2.BIN` | 524,288 bytes |
| SC-55 | `ROMS/SC55/WAVE1.BIN` | 2,097,152 bytes |
| SC-55 | `ROMS/SC55/WAVE2.BIN` | 1,048,576 bytes |
| SC-55 | `ROMS/SC55/SUBCPU.BIN` | 4,096 bytes |

The loader checks file sizes and reads; Munt also validates its ROM pair. These
ROMs are not included. Missing assets produce an on-screen and serial message
and return to the menu. The 36 existing MT-32 MIDI files and the existing
Warcraft SC-55 score are included. SC-55 renders audio offline before playback.

Three soundtrack headers were absent from the upstream repository:
`fighting_back.h`, `sortie.h`, and `step_on_beat.h`. Their affected FM/PSG slots
use an original synthesized test tune generated by
`scripts/pine64_demo_music.py`, and their screen titles identify that tune.
The original NES/GB tracks that were present are retained.

See [EXTERNAL.md](EXTERNAL.md) for the actual A64 Si5351/YM3438 and N64 wiring.
Mercury shares PC0, PC2 and PC3 (Pi-2 pins 19, 23 and 24) with that optional
YM adapter; disconnect one adapter before using the other. Logical keyboard controls do not implement the original physical
NES/SNES/Genesis GPIO adapters. Physical N64 is a separate optional PH9 path.

See [AUDIO_CEDAR.md](AUDIO_CEDAR.md) for analog audio, SC-55 and Cedar details.
The A64 Cedar sprite demos use actual CPU I_PCM H.264 encoding followed by
Cedar hardware decoding, labeled on screen. A64 hardware encoding is not
claimed. The source's "Cedar JPEG" slot is accurately labeled H.264 decode.

## Mercury with the existing Pico / SpotPear firmware

Keep the Pico firmware and SpotPear HDMI connection that already display the
cube on your TV. The PINE menu sends the **existing branch's display lists**
to that firmware; it does not install a new Pico protocol or require a UF2.
The newest `mercury/` tree is retained unchanged, including the Pico 2 W
presets, HSTX alternative, PicoDVI SRAM execution and frame-boundary swaps.

For the branch's default **SpotPear** build, the PINE side is:

| Signal | PINE A64 Pi-2 pin | A64 GPIO | Existing Pico GPIO |
|---|---:|---|---|
| MOSI / Pico RX | 19 | PC0 | GP4 |
| SCK | 23 | PC2 | GP6 |
| CS, active low | 24 | PC3 | GP5 |
| Ground | 6, or another GND pin | GND | GND |

Use 3.3 V signals and a common ground. **MISO is unused and READY does not
exist in this protocol.** The host leaves PC1 and PC4 untouched. If the
existing Pico uses the DVI_SOCK, AMY or LEGACY_GP0 preset instead, its receive,
clock and CS pins are GP8, GP10 and GP9 respectively; its TV wiring remains
as built. Do not use the old proposed GP8/9/10/11 + GP12 READY wiring for a
SpotPear board: GP8–15 carry its HDMI signal.

Each transfer is mode 0, MSB first, with a two-byte little-endian payload
length followed by up to 4096 display-list bytes under one continuous CS
assertion. The A64 master runs at 1 MHz and holds CS low for 25 ms before
clocking, giving the existing polling receiver time to finish its self-test
frame. Hardware bursts are bounded and CS is released on every error. This
conservative pacing accommodates the receiver's polling design; it provides no remote
acknowledgement or readback guarantee.

Selecting **Mercury GPU Bring-Up** sends the latest demo's dusk-coloured cube
instead of the Pico's autonomous primary-coloured cube. Pause and scene-switch
controls let you check that the TV follows PINE commands. The PINE HUD counts
**local lists/bytes sent**, and displays local-controller errors. Those counts
cannot prove that an unplugged or busy Pico accepted the scene.

### Why the TC358743 return path cannot feed this A64

The latest V3s route is Pico HDMI → TC358743 → MIPI CSI-2 → V3s receiver.
The A64 camera input is **8-bit parallel CSI / BT.656**. Its MIPI DSI block is
a display transmitter, not a CSI-2 camera receiver. Consequently, the existing
TC358743 CSI-2 output cannot connect directly to the PINE A64 camera input.
The PINE demo leaves all V3s CSI-2 / D-PHY registers untouched and explicitly
reports that capture is unavailable. It does not draw a locally rendered cube
and label it a captured Pico frame. Direct Pico-to-TV output still works.

The optional **V / N64 C-Up** diagnostic reads a TC358743 at address `0x0f`
or `0x1f` using Pi-2 **pin 5 PH2/SCL** and **pin 3 PH3/SDA**, with external
pull-ups to 3.3 V. It reports acknowledged chip ID, raw HDMI status and detected
active size, or an I2C error. This read-only check restores those GPIO settings
on return; it does not reset/configure the bridge or enable CSI transmission.
A bridge that has not been configured may report no HDMI lock. HDMI lock is
not evidence of a frame captured by the A64.

[Toshiba's TC358743XBG specification](https://toshiba.semicon-storage.com/us/semiconductor/product/interface-bridge-ics-for-mobile-peripheral-devices/hdmir-interface-bridge-ics/detail.TC358743XBG.html)
identifies its conversion as HDMI input to MIPI CSI-2 output.

Hardware references: [Allwinner A64 User Manual v1.1](https://linux-sunxi.org/images/b/b4/Allwinner_A64_User_Manual_V1.1.pdf),
§2.1.7.1 (printed p.66), §5.1.1–5.1.2 (pp.475–477), and display block diagram
Fig.6-1 (p.498); [mainline A64 device tree](https://github.com/torvalds/linux/blob/master/arch/arm64/boot/dts/allwinner/sun50i-a64.dtsi),
`csi_pins`, `csi@1cb0000`, `dsi@1ca0000` and `dphy@1ca1000`.
The PINE header mappings follow the
[PINE A64 pin assignment](https://files.pine64.org/doc/Pine%20A64%20Schematic/Pine%20A64%20Pin%20Assignment%20160119.pdf).

## Rebuild

A PINE menu source snapshot, including the required modified/pinned Munt,
Nuked SC-55 and TinyUSB source and their licenses, accompanies the firmware.
Use GNU Arm Embedded GCC with its hard-float Cortex-A53 multilib, Newlib and
libstdc++; the delivered build used GCC 13.2.1 and Newlib 4.4.0. `mkimage`
from U-Boot tools generates the boot wrappers.

```bash
make BOARD=pine64 -j6 boot
```

Outputs: `build/pine64/jupiter.{elf,map,bin,uImage}` and
`build/pine64/boot.scr`. There is no Linux root filesystem. The original V3s
build remains behind the default board selection. The Pico firmware source
in `mercury/` remains exactly the latest branch; its build options are in
`mercury/README.md`. The PINE update does not require rebuilding or flashing it.

## Validation boundary

The earlier SD2 CPU/AArch32/NEON/SD bring-up was observed on the user's board.
The newly ported menu, Mercury, USB PHY setup, audio, Cedar decode, scaling and
external GPIO paths still need a physical run in this combined image.

The supplied logs record target compilation, AArch32 startup/MMU/GIC/VFP QEMU
checks, actual OHCI/TinyUSB keyboard transactions in QEMU, SD timeout/capacity
unit tests, display register-model tests, external-device protocol tests,
Cedar I_PCM decode checks and SC-55 driver fixtures. New branch integration
checks cover the existing Mercury packet format and PINE SPI timeouts,
input settling, CPak bounds, memory tails and A64 display-mode registers.
Tests never write a physical SD card, and emulated peripherals do not
establish electrical behavior. A64 color-key semantics, NV12 color matching
and mid-frame scan-address latching remain physical bring-up tests.
